# feature-analyze — 新特性前置分析

对新特性做**动手前的影响分析**：澄清需求 → 对照现有代码找疑问 → 评估影响面与风险 → 给建议。**只输出报告，不做任何修改。**

## 铁律

- **只诊断分析，不修改任何东西**。不改源码、数据库、配置、路由；不新增文件；不执行迁移。
- 报告里所有问题都必须附一句简短的 AI 建议（给倾向性判断，不要只抛问题）。
- 结论要能给用户"值不值得做 / 怎么做更简单"的明确判断，而不是罗列选项。

## 调用方式

```
/feature-analyze <新特性描述>
```

## 工作流

### Step 1 — 先建立"项目现状"认知（不要凭记忆）

动手分析前先摸清现状，重点看：
- 项目根 `CLAUDE.md` 与 `backend/CLAUDE.md`（架构、设计决策、已知陷阱）
- 后端 `backend/app/models/__init__.py` + `database.py`（表结构、字段）
- 后端 `backend/app/api/` 下路由清单（现有接口能力）
- 后端 `backend/app/services/` 下业务模块（生成链路、注册表、安全、快照等）
- 前端 `frontend/src/` 的路由、页面、状态管理、API 调用层
- 用 `grep`/`rg` 确认需求涉及的能力是否已存在（为"重复造轮子"做准备）

### Step 2 — 按用户描述逐项分析，产出报告

输出统一模板（见下）。核心是**四组问题必须给 AI 建议**：

## 报告模板

```markdown
# 新特性前置分析 — {特性名}

> 只输出分析，不做任何修改。

## 一、需求澄清问题
对用户描述中**不明确/有歧义**的点提问（针对问题本身，不涉及代码）：

- **Q1**：……
  - **AI 建议**：……
- **Q2**：……

## 二、结合现有代码的疑问
分析项目现状后发现的、与现有实现冲突/需要确认的疑点（每个都要指出对应文件/模块）：

- **Q1**：现有 `xxx.py` 的某机制是否与这个需求冲突/复用？
  - **AI 建议**：……
- **Q2**：……

## 三、可维护性 / 可扩展性 / 重大变更
逐项评估，**明确标注是否有重大变更**（尤其数据库）：

- **数据库/数据层**：是否新增/修改表、字段、索引？SQLite 无自动 migration——新增字段需评估加列脚本与存量数据默认值；是否动到 `pages`/`users` 等多处引用的表
- **API 契约**：新增端点 vs 修改现有端点？是否改变请求/响应结构（前端已对接的会直接崩）？
- **前端状态**：是否新增全局状态/Context？是否跨组件共享？
- **路由/URL**：是否新增路由？是否与 `/{user_id}`、`/{user_id}/{page_id}` 路径冲突（该项目 URL 方案有讲究）？
- **安全**：是否扩大公开暴露面？是否触碰 content filter / 发布扫描 / iframe sandbox / proxy SSRF / 用户上传（magic bytes 校验）？
- **依赖**：分两种看——
  - 生成侧：新特性是否需要在 **LLM 生成的 HTML** 里新增 CDN 库？若是，必须进 `library_registry.py` 注册表（含 access 模式/usage_notes），这是硬约束；
  - 开发侧：新特性是否需要新增 npm/pip 依赖？常规考量，无特殊红线，评估体积与维护成本即可
- **可扩展性**：实现是否便于以后演进（配置驱动 / mock 与真实切换 / 模块复用）？
- **可维护性**：改动是局部还是散落多处？是否符合现有设计决策（SSE 协议、两步 LLM、加密 API key 等）？

结论里明确：**整体是否算"重大变更"**（涉及数据库字段变更即至少算中高影响）。

## 四、影响面清单（细分到二级）

按 8 个一级维度列二级明细，未涉及的维度写明"无影响"：

| 一级 | 二级 | 影响说明 |
|---|---|---|
| 前端 UI | 组件 / 页面 / 样式 | …… |
| 前端路由 | 新增路由 / 路由参数 / 路径冲突 | …… |
| 前端状态 | Context / 本地状态 / URL query 状态 | …… |
| 后端接口 | 新增端点 / 修改端点 / 请求响应契约 | …… |
| 后端数据库 | 表 / 字段 / 迁移 / 存量数据 | …… |
| 安全 | 内容安全 / 上传 / 公开暴露面 / SSRF | …… |
| 依赖 | 生成侧 CDN 注册表 / 开发侧 npm·pip | …… |
| 配置 | .env / PUBLIC_BASE_URL / 环境 | …… |

## 五、风险与回归
会不会破坏现有功能，逐项检查：
- **已发布页面**：`/{user_id}/{page_id}` 公开页是否受影响？
- **SDK 注入**：`window.platform` 注入链路是否被波及？
- **封面快照**：Playwright 截图链路（内部 render 端点 + JWT header 鉴权）是否被波及？
- **生成链路**：SSE 事件协议（progress/token/final/done/error）是否被改？
- **mock 模式**：`/api/mock/generate` 与真实链路是否被改？
- 其他：登录/JWT、头像上传、page_id 301 重定向、LLM 配置两级优先级

## 六、备选方案
同一个需求有没有更简单的做法：
- 是否可以用 **mock 先验证**（`/api/mock/generate`）？
- 是否**改配置/改注册表**即可，而非新建模块？
- 是否可以先做**最小可用版**，再迭代？
- 给出你认为的**推荐路径**（一句话）。

## 七、重复造轮子检查
grep 现有代码后确认：这个能力是否已以某种形式存在（如已 API、已 service、已前端组件）？
- 已存在 → 说明在哪里、如何复用；
- 不存在 → 明确说"无现成实现"。

## 结论
- **整体评价**：建议做 / 简化后做 / 暂不建议
- **必须澄清的 1-2 个点**（最短路径，问清即可开工）
- **主要风险一句话**
```

## 注意事项

- **每个问题都要有 AI 建议**，不要只罗列疑问让用户自己想。
- 提问要克制：不明确点问清，但**不要为了凑数提问**；能给默认假设的（如"建议默认按 X 做"）就直接给建议。
- 影响面清单**必须细分到二级**，未涉及维度写"无影响"，不要留空。
- 报告用中文；代码、文件路径、库名用英文。
- 若新特性描述本身过于模糊、无法开始分析，先在报告开头列出"最短需要澄清的问题"，再按能合理假设的部分继续分析，不要拒绝分析。
